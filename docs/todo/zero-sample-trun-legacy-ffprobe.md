# 记录：旧版 ffprobe 被零样本 trun 阻断（暂不修改）

**状态：根因已通过实际旧版二进制与结构对照确认；本文仅记录，暂不修改录制、解析或保存逻辑。**

## 结论

Chrome 当前生成的分片 MP4 中，音频轨存在 `sampleCount=0` 的空 `trun`。Memo 自带的 **ffprobe 4.0.2（2018）** 无法正确处理这些空运行片段，于是在读取 MP4 头时失败：

```text
[mov,mp4,m4a,3gp,3g2,mj2 @ …] error reading header
…: Operation not permitted
```

这不是 Windows 文件权限问题，也不是所有 fMP4 都不受支持，更不是 H.264/AAC 编码或 DTS 重复损坏。**触发条件是零样本 `trun`，不是单独 `tfdt=0`。**

## 实测样本

文件名：`TabRecord_2026-10-28T13-14-00.mp4`

- 大小：`2,475,719,551` 字节
- 时长：`10799.846300` 秒
- SHA-256：`89a4fb3dc33ab414354ad446c8955441e4953da965c61e46c42e8db6afe8e571`
- 视频：H.264 / 1920×1080 / `time_base=1/30000`
- 音频：AAC / 48000 Hz / 单声道

顶层结构已经直接读取确认：

```text
ftyp @ 0
moov @ 36（1212 字节）
moof @ 1248
mdat @ 4452
后续为 moof + mdat 重复，共 6119 对
```

所以该文件的 `moov` **已经在文件头**，不能用 `moov-at-end` 解释 Memo 的失败。`moov` 中有 `mvex`，普通 `stbl` 样本计数为 0；这对 fMP4 是正常的，实际样本信息位于各分片的 `traf/trun` 中。

## 根因证据

### 1. 同一旧版 ffprobe 直接复现

使用用户提供的实际附件：`ffprobe 4.0.2`，配套 `ffmpeg 6.0`。

| 输入 | ffprobe 4.0.2 结果 |
|---|---|
| 原始 MP4 | 退出码 1，`error reading header` / `Operation not permitted` |
| 新版 FFmpeg 生成的普通 MP4 样本 | 退出码 0，正常读取 H.264/AAC 和时长 |

因此可以排除 Memo 所在机器的路径和 Windows 权限作为根因。`Operation not permitted` 是这条 MP4 解析路径返回的错误文本，不能直接当作文件访问权限结论。

### 2. 空 `trun` 的位置与字段

扫描全部 `moof` 后，发现 4 个 `sampleCount=0` 的音频 `trun`，均带 `tfdt=0`：

| moof 起始偏移 | 轨道 | 含义 |
|---|---|---|
| 282838231 | 2（音频） | 空 `trun` |
| 565309293 | 2（音频） | 空 `trun` |
| 2475475918 | 2（音频） | 空 `trun` |
| 2475587197 | 2（音频） | 空 `trun` |

全部 `trun` 的样本偏移都在合法范围内，没有发现会寻址到文件外的结构。末尾空 `trun` 的 `dataOffset` 指向分片末尾或文件末尾，但没有样本需要读取。

### 3. 最小结构对照实验

在**副本**上做等长替换，原文件不改：

| 实验 | 结果 |
|---|---|
| 只把末尾两个空 `trun` 改为 `free` | 仍失败，因为中间还有两个空 `trun` |
| 只把末尾两个空 `traf` 改为 `free` | 仍失败 |
| 只把末尾两个 `tfdt=0` 改为非零 | 仍失败 |
| 把全部 4 个空 `trun` 等长改为 `free`，不改变任何偏移 | **ffprobe 4.0.2 成功读取** |
| 只把全部 4 个 `tfdt=0` 改为非零，保留空 `trun` | 仍失败 |

这证明：**零样本 `trun` 是关键触发因素，不能通过只改 `tfdt` 解决。** `trun → free` 仅用于定位根因，不是通用生产修复。

## 与其他问题的区别

- **不是 `moov` 缺失或位置问题**：当前样本 `moov` 在前。重封装样本即使 `moov` 在末尾也能被旧版读取，说明 faststart 不是 Memo 能打开的必要条件。
- **不是 DTS 重复或倒退**：全文件 312,114 个视频包 DTS 均严格递增，重复和倒退均为 0。
- **不是解码失败**：使用新版 FFmpeg 对整段约 3 小时音视频做完整解码，退出码 0，标准错误输出为 0。
- **不是单纯 `tfdt=0`**：只改非零不能使旧版 ffprobe 成功；`tfdt=0` 还可见于正常起始分片。
- **不是普通 MP4 与 fMP4 的简单二选一**：`mvex`、空 `stbl` 和 `trun` 的组合需要解析器正确处理；不能笼统宣称所有分片 MP4 都有问题。

此前 `-f null -` 输出中的大量非单调 DTS 警告，已另行确认主要是 FFmpeg 默认输出时间基换算造成的，与这里的旧版零样本 `trun` 失败不是同一根因。

## 零样本 `trun` 的意义与影响

`trun` 描述轨道分片中的一段连续样本；`sampleCount=0` 表示该运行片段没有样本。它可能是封装器保留轨道/分片状态、处理边界或刷新缓冲区时产生的空占位。

在这份样本中，它们没有音视频负载，也没有携带有效时间轴内容，更像封装副产品，而非为对齐音视频所必需的数据。现代解析器通常能容忍它们，但旧版 ffprobe 可能无法读取整个文件。它们本身只占很少字节，不能说明画面、声音或时间戳必然损坏。

当前 `mp4-faststart.js` 只修补 `moov` 时长，保留 `moof/mdat`，没有新增这些空 `trun`。

## 为什么 `-c copy` 和升级工具能解决

- 新版 ffprobe 能处理这些空运行片段。
- `-c copy` 重封装时，FFmpeg 去掉 `moof` 分片结构，重新建立普通 MP4 的完整样本索引表（如 `stts/stsc/stsz/stco`），因此旧版解析器也能读取。
- 音视频压缩数据不变，不需要通过 `libx264` 重编码解决。

## 当前处理决定

**暂不修改现有实现。** 对需要兼容 Memo 的文件，使用新版 ffprobe 或 `-c copy` 重封装即可。

暂不建议为了旧解析器全局删除所有空 `trun`、强制所有 MP4 走 wasm，或把 `trun` 直接改成 `free`。这些做法分别涉及兼容性、资源成本和通用正确性风险。

## 如果以后实现兼容修复

### 方案 A：保留 fMP4，过滤零样本结构

不能只改 `tfdt`，也不能只删除 4 个字节了事。正确实现需要处理：

- `traf` / `trun` 删除后的 `moof` 大小；
- `trun.data_offset` 与其他相对偏移；
- `mfra/tfra`（如果存在）；
- 多轨道、多个 `trun`、不同 `tfdt` 和索引语义；
- 不改变实际媒体负载、时长与音画同步。

### 方案 B：提供普通非分片 MP4 兼容输出

可以复用现有 FFmpeg/FFmpeg.wasm 的流复制重封装思路，但会加载内核、完整读入并写出文件，增加保存耗时、内存与 GB 级失败风险。应做成可选能力，失败保留原文件，并明确显示保存进度，不能悄悄改变所有用户的输出路径。

### 方案 C：纯 JS 去分片

需要重建普通样本表与偏移，复杂度最高。除非明确要去除 FFmpeg 依赖，否则不应仅为这一旧版兼容问题引入整套重写。

## 后续验收要求

1. 覆盖音频与视频轨、文件开头/中间/结尾的空 `trun`，以及 `tfdt=0` 和非零情况。
2. 覆盖多 `traf`、多 `trun`、有无 `mfra`、普通 fMP4 与 moov-at-end fMP4、截断输入。
3. 旧版 ffprobe 4.0.2 能读取元数据，新版 FFmpeg 能完整解码；实际 Memo 能打开并转写。
4. 媒体负载逐字节一致，时长、索引、音画同步与拖动正常；不得引入非递增 DTS。
5. 对长视频验证内存和保存耗时；失败时保留原始文件，不伪造成功状态。
