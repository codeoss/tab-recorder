# 长录制持续暂存与异常恢复设计

**状态：已实施；2026-11-06 已完成 Linux/CfT 158 的 4.5 小时 WebM 实测（23.66 GB），以及本地 Google Chrome 156 保留其他扩展的 NBC 直播 5 小时 10 分实测（16.81 GB），均正常保存且未复现崩溃。2026-11-07 本地 Chrome 156 原生 MP4 在 4,294,540,012 字节（2³²−427,284）处 SIGTRAP，OPFS 恢复保存成功；根因为 Chrome 的 32 位输出计数器，上游提交 `3f057555` 已修复，详见 `docs/todo/native-mp4-4gib-chrome.md`。Windows 与 RDP 仍待验证。**

## 背景与证据

Linux 下连续录制数小时后，扩展需要 reload，且没有下载文件。当前 `core-recorder.js` 把整段录制的 Blob 保留在 `chunks` 中；每 60 秒的 `compact()` 只减少 Blob 对象数量，不减少媒体负载。只有 `onStopped()` 才进入修复和下载，因此 offscreen、Chrome 或系统异常终止时，没有扩展管理的可恢复文件。既有 E2E 是秒级测试，不能证明数小时录制可靠。仅凭这次现象还不能断定 Linux OOM 是唯一根因。

临时自动化探针已验证：

- 普通 OPFS `createWritable()` 写入但未关闭时，文件在浏览器重启前后均为 0 字节，不能用作崩溃暂存。
- Dedicated Worker 的 `createSyncAccessHandle()` 写入并 `flush()`，即使不关闭句柄，3 MiB 数据在整浏览器重启后仍逐字节完整。
- 真实 VP9/Opus MediaRecorder 录制约 6.3 秒，未停止就关闭浏览器后，329 KB 左右的原始 WebM 可以恢复、补索引并下载；完整解码退出码为 0，但 FFmpeg 报告 `File ended prematurely`。尾部恢复必须单独处理，不能直接采用探针作为生产实现。
- offscreen 中不能直接使用 `chrome.storage.local`，恢复元数据需要经 background 或采用其他持久化方式。

## 目标

1. 录制过程中持续保存完整分片到扩展管理的 OPFS，内存占用不随整段时长线性增长。
2. 正常停止后仍输出一个完整文件，沿用现有 WebM/MP4 修复、下载确认和历史记录，不改变格式与画质。
3. offscreen 被销毁、扩展 reload、Chrome 崩溃或浏览器重启后，能发现上次未完成录制，并由用户明确恢复保存或丢弃。
4. 录制、整理、恢复和下载期间均有可见状态；失败不能静默退回无保护的长录制。
5. 恢复只保留结构完整的数据，不伪造帧、索引、时长或下载成功状态。

## 非目标与边界

- 无法恢复本次已经 reload 且未暂存的录制。
- 不自动分段，不重编码，不新增 ffmpeg.wasm 使用、npm 依赖、网络请求或扩展权限。
- 不承诺抵御断电、磁盘损坏、浏览器存储被清除等所有故障；OPFS 持久化是降低丢失窗口，不是绝对保证。
- 不把短段合成媒体测试当成真实数小时验证；Linux 已完成 CfT 4.5 小时及品牌 Chrome 5 小时 10 分 WebM 实测，但 Windows、MP4 和 RDP 仍需单独验收。

## 方案比较

### 采用：Worker 同步 OPFS 暂存 + 恢复导出

每个 MediaRecorder 分片经有界队列转交 Dedicated Worker，以 sync access handle 追加写入并 flush。正常保存从 OPFS 获取 File/Blob，异常后从持久元数据找到它。能保留单文件体验，并覆盖浏览器进程异常，改动集中在录制缓冲、状态和恢复入口。

### 备选：定时自动分段

每 15–30 分钟停止并下载一段，再开始下一段。实现较直接，但分段轮换可能产生音画间隙，会改变输出为多个文件，而且当前段仍有丢失窗口，因此不作为本次根修。

### 排除：普通异步文件流

`createWritable()` 未关闭时探针重启后得到 0 字节，不能满足异常恢复。仅增加内存警告、看门狗或更频繁 compact 也不能恢复已经丢失的 Blob。

## 具体设计

### 持续暂存

- 新增小型 IIFE 适配模块和经典 Worker 脚本；HTML 按现有依赖顺序加载，Worker 不访问 `chrome.*`。
- 每个非空 `ondataavailable` 分片按顺序执行 `Blob.arrayBuffer()`，以 transferable 转交 Worker，按预留偏移完整写入并 flush；收到确认后才释放该分片。
- 不再永久保留整段 `chunks`。主侧只保留有限待写队列；设定明确的待写数量/字节上限。写入持续落后、磁盘不足或 Worker 失败时停止继续无保护录制，保存已确认前缀并显示错误，不能悄悄累积内存。
- 首版每个分片 flush，以真实吞吐测试决定是否调整；不在未验证时引入更大的丢失窗口。
- 每次新录制使用唯一目录和元数据，避免覆盖上次尚未处理的文件。记录格式、Mime、开始时间、最后确认字节数、实际媒体时长、保存阶段和 downloadId。

### 正常保存

- `recorder.stop()` 后等待最后一个 `dataavailable`、队列清空和 Worker 确认，再关闭写入句柄并进入现有 `onStopped` 修复链。
- OPFS File 是 Blob，可直接供现有流式 `fixWebMBlob` / `mp4FaststartJs` 使用；最终 Blob 在下载成功前继续保留，现有保存状态窗口与重试规则不变。
- 只有真实下载 `complete` 后才写成功历史并清理暂存。整理、下载或浏览器中断时保留原始与已整理产物，恢复时先对账已有 downloadId，避免重复下载和重复历史。
- 原始文件至少保留到最终下载成功；需要为原始文件、整理产物和下载目标评估磁盘空间，不假装零拷贝或零额外占用。

### 异常尾部

- 将异常恢复与正常 WebM 修复分开验收。先为“不完整 Block / BlockGroup / Cluster、未知长度末尾 Cluster、最后一个完整分片”建立失败用例和真实浏览器样本。
- 前向解析到已确认字节边界，只截去结构不完整的尾部；不得仅因 FFmpeg 警告就删除整个最后 Cluster，也不得修改完整媒体负载。
- 若末尾未知长度 Cluster 的全部子元素完整但容器未结束，使用等宽、可验证的 EBML 收尾方式消除 `File ended prematurely`；保持既有 Cue 偏移规则，legacy/golden 与流式路径行为一致。
- 修复后 Duration 来自最后确认的媒体时间，而不是包含浏览器关闭期间的墙钟差。恢复文件必须通过完整解码、帧数/时长合理性和关键帧 Cue 校验。
- 原生分片 MP4 走独立的截断与现有 faststart/时长修复验证；不把 WebM 结论直接套到 MP4。老 Chrome 的事后 wasm 转码行为保持原样。

### 状态与恢复入口

- background 通过 `chrome.storage.local` 保存跨浏览器重启的恢复元数据；`storage.session` 继续承载当前会话状态，不能作为唯一恢复记录。
- 录制中显示“已暂存”字节数；写入异常显示“暂存失败/磁盘不足”。启动时无法建立受保护暂存则不开始长录制，并给出明确原因。
- 扩展启动或打开主界面时发现未完成录制，显示“发现未完成的录制”、大小和时间，提供“恢复保存”和需确认的“丢弃”。恢复期间复用独立保存窗口，完成前不允许新录制覆盖它。
- 用户明确丢弃才删除对应暂存；恢复失败保留文件供重试。UI 不把暂存字节数称为已下载，也不把开始下载称为已保存。

## 验证

1. 先运行失败回归：普通异步流、真实 WebM/MP4 不完整尾部、录制中强杀测试专用浏览器、offscreen 销毁和扩展 reload。区分优雅关闭与真正进程强杀，不用 `ctx.close()` 冒充所有崩溃。
2. 持续写入单元测试覆盖短写、flush、队列背压、写入失败、元数据恢复和清理；所有现有单元测试保持通过。
3. 浏览器故障测试验证恢复文件可完整解码、无意外提前结束警告、时长与关键帧正确；正常 WebM、原生 MP4 和现有 A–E 场景不回归。
4. 测试恢复保存、重复恢复、下载中断后重启、失败重试、明确丢弃，确认不重复历史、不重复下载、不误删文件。
5. 以高码率真实 tabCapture 检查写入吞吐、队列和内存；再分别完成 Windows 与 Linux 长录制实测。没有长录制证据时明确保留限制。

## 交付顺序

先完成异常尾部与真实媒体故障测试，再接入有界 OPFS 暂存，随后接入恢复 UI 和下载对账，最后跑完整回归与长录制验证。每一阶段都保留可运行基线，不用临时探针替换现有可靠保存链。
