# 可选按时间分段录制设计

**状态：已实现默认关闭的同流重叠分段；秒级真实媒体与多分段恢复已验证，分钟级长录制、单段超过 4 GiB、真实 RDP 和 Playwright 之外的最终文件名仍待验收。**

## 意图与背景

用户需要一个可选的按时间分段功能，例如每 30 分钟生成一个独立文件。最新根因文档 `docs/todo/native-mp4-4gib-chrome.md` 已证明：受影响 Chrome 的原生 MP4 在单个封装任务累计超过 `2³²` 字节时会触发 renderer SIGTRAP。分段会创建新的 `MediaRecorder` 和封装任务，因此可绕过该边界；分段也让长录制产物更容易管理。

该功能是用户主动选择的产物形态变化，不是默认修复。首选仍是升级包含 Chromium 提交 `3f057555` 的 Chrome；不分段的长录制继续使用既有路径。

## 目标

1. 提供独立「分段录制」开关，默认关闭；打开后才显示分钟数，默认 30 分钟。
2. 分段时复用同一媒体流，先启动下一段，再停止上一段；上一段整理与下载期间，下一段不停止。
3. 每段都是可独立播放的 WebM 或 MP4，经过既有索引/时长修复和真实下载确认。
4. 标签页、窗口/屏幕和兼容模式使用同一分段控制器，不重新取流或要求新的选屏手势。
5. 暂停、总定时停止、手动停止、保存失败、异常恢复和明确丢弃均有确定的会话级语义。
6. 保存中的分段与当前录制状态同时可见，不把开始下载称为已保存。

## 非目标与边界

- 不默认开启，不用 `0` 表示关闭，不改变既有单文件录制行为。
- 不承诺多个文件在采样级无缝；重叠切换避免主动留出保存间隙，但编码时间戳仍可能存在微小重叠或空洞。合并文件需要另行重封装，不在本功能内。
- 不自动合并、重编码或增加 ffmpeg.wasm 使用，不新增权限、依赖、网络请求或 `web_accessible_resources`。
- 时间分段不是大小保证。分钟数过大时，单段仍可能超过 4GiB；旧版 Chrome 原生 MP4 的界面提示建议 30 分钟或更短，并仍建议升级 Chrome。
- 已成功下载的分段不会被「丢弃」删除；明确丢弃只取消当前会话并删除尚未保存的分段。

## 方案比较

### 采用：同一媒体流上的重叠切换 + 串行保存队列

分段控制器先建立并持有唯一媒体流。到达边界时，先为下一段创建 `MediaRecorder` 和独立 OPFS writer，确认下一段开始后再停止上一段。上一段进入既有修复链，下载按段号串行执行，避免 background 同时处理多个下载状态。

优点是不会因整理/下载主动停止画面，且桌面与兼容模式无需重新选屏。代价是需要会话控制、多个暂存项和分段状态协议。

### 备选：停止、整理并下载完再开始下一段

可复用单任务状态，但保存期间没有录制，会产生明显内容间隙；在浏览器中重复取流还会引入手势和音频回环问题。不符合本次选择。

### 排除：直接切割 MediaRecorder 的 Blob 分片

媒体头、时间码和索引属于整个容器，不能把任意分片直接当作独立文件。这样做需要完整的容器重封装，风险和复杂度都高于重叠创建录制器。

## 具体设计

### 设置与界面

- `recorderSettings` 新增 `segmentEnabled: false` 和 `segmentMinutes: 30`。
- popup 在定时停止附近显示「分段录制」开关；仅开关打开时显示分钟输入框。
- 分钟数为 1–1440 的整数；无效值在开始时明确提示，不静默改成关闭或 0。
- 分段状态显示当前段号、已完成段数和保存队列；录制中保存上一段时显示「正在保存第 N 段，录制继续」。
- 设置仍只写 `chrome.storage.local`，不改变其他设置的默认值。

### 会话与重叠切换

- 新增经典 IIFE 模块 `segment-recorder.js`。开关关闭时，offscreen/recorder 继续直接调用 `createRecorderEngine`；开启时才创建会话控制器。
- 控制器只调用宿主的 `getStream` 一次。每段使用独立的核心引擎和 OPFS writer，但共享该媒体流。
- 核心引擎增加明确的资源所有权选项：分段停止只释放本段 recorder/writer，不停止共享媒体轨，也不调用宿主的音频回环/兼容流清理。只有整个会话结束或明确丢弃时，控制器统一释放这些资源。
- 切换顺序为：创建下一段 writer → 创建并启动下一段 recorder → 确认开始 → 停止上一段。下一段启动失败时先不停止上一段；但不得无限重试或让旧段继续增长，应立即停止会话并保存上一段，显示明确错误（此项为实现者按安全边界作出的选择）。
- 每段有独立 `recordingId`、`segmentIndex`、`startedAt`、确认字节和最终 Blob；文件名在扩展名前加入 `_part001`、`_part002` 等。
- 会话控制器负责总计时、暂停累计和总定时停止，核心引擎的段内 tick/限时消息不直接重置全局计时。

### 保存队列与状态协议

- 每段停止后沿用既有 `finalize → WebM 修复/MP4 faststart → 下载 complete` 链；保存函数按段号串行执行。
- 保留老 Chrome 的 WebM→MP4 ffmpeg.wasm 回退，但转码也进入同一串行队列。最多允许一个待处理旧段和一个活动段；到达新边界时旧段仍未到可下载终态，则停止当前段、完成可完成的保存并显示「处理速度跟不上分段录制」，不得继续堆积任务（此项为实现者按资源上限作出的选择）。
- 上一段的 `processing/stopped/saved` 不得把整个会话改成 `idle`。新增段级消息或在现有消息中携带明确的 `sessionId/segmentId/segmentIndex` 与 `scope: 'segment'`。
- background 继续只启动一个实际下载，保存队列提供互斥。`SEGMENT_SAVED` 只在下载 complete 后写历史，`recordingId` 保持去重。
- `state.status` 在分段保存期间仍为 `recording` 或 `paused`；同时展示段级保存阶段和真实下载进度。最终停止必须等待所有已完成录制分段保存到终态。
- 若旧段下载失败，不再创建新段，并停止当前段，进入既有可见错误/重试状态；失败产物和 OPFS 保留，不能继续无限积累待保存队列。
- 若当前段的 writer、worker 或取流失败，按既有媒体错误链停止会话并保存已确认前缀。

### 多分段暂存与异常恢复

- 现有 `durableRecording` 单对象无法同时表示「正在录制的下一段」和「正在下载的上一段」。引入按 `recordingId` 索引的分段集合（或等价数组），每项沿用既有元数据、确认字节、phase、downloadIntent 和 downloadId。
- 读取时兼容既有单个 `durableRecording`，迁移为集合后再处理；老版本未完成的单段录制仍可恢复。
- `DURABLE_UPDATE` 只能更新同 id 项，`DURABLE_CLEANUP` 只能删除同 id 项；不得再因 id 不同而拒绝同一会话的合法相邻分段。
- 重启后按 `sessionId + segmentIndex` 排序，逐项先对账已有下载，再恢复未下载项；每项 complete 后才删除对应 OPFS 和历史待恢复项。集合为空才清除会话恢复状态。
- 重复恢复使用同一互斥锁，历史按 recordingId 去重；不能因多段而重复下载、重复写历史或提前报告全部恢复完成。
- 界面显示未完成分段数量和总确认字节。恢复/丢弃期间继续禁止新录制。

### 控制语义

- **暂停/恢复**：只暂停当前活动段，分段计时和总计时均排除暂停时长；暂停期间不发生边界切换。
- **定时停止/手动停止**：不再开启下一段，当前段停止后等待保存队列完成，再释放共享媒体流并上报会话结束。
- **丢弃**：停止当前段，删除所有尚未下载完成的分段和对应恢复项；已经下载完成的文件保留，确认文案明确这一点。
- **空段**：没有有效媒体数据的最终段不下载、不写成功历史，但仍需完成清理。

## 验证

1. 先写失败单元测试：开关默认关闭、分钟输入显示与校验、配置持久化；重叠顺序、段号、总计时、暂停、总限时、保存串行和失败停止。
2. 用可控 MediaRecorder/OPFS/下载边界验证：下一段已开始后旧段才停止；旧段停止不结束共享流；任何 `saved` 都对应真实 complete。
3. 覆盖下载失败、Worker 失败、最终停止与切换竞态、丢弃、空段和重复事件；不得出现孤儿录制、重复历史或跨段误删。
4. 覆盖两个以上未完成分段的强杀恢复、已有下载对账、顺序恢复及旧版单 `durableRecording` 迁移。
5. 真实浏览器用缩短的测试分段间隔分别跑 WebM 与原生 MP4，至少产生 3 段；验证每段独立解码、时长、音视频、WebM 关键帧 Cues 和 MP4 faststart。
6. 运行完整 `npm test`，再在真实 Chrome 验证开关默认关闭、30 分钟设置、状态可见和长录制。必要时用真实 YouTube TV 做长测，但短测试不能冒充 4GiB 验收。

## 交付顺序

先实现设置和会话控制器，再接入段级保存与多分段恢复，最后完成真实媒体验证。每一步保持默认关闭的旧路径通过现有测试；发现无法保证重叠或恢复语义时停止交付，不退回带保存间隙的方案。
